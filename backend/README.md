# EduFlow authentication setup

Authentication uses PostgreSQL, Argon2id password hashes, short-lived access JWTs, and rotating refresh tokens in an HttpOnly cookie.

## Local development

1. Copy `backend/.env.example` to `backend/.env`. Set a PostgreSQL `DATABASE_URL` (for Neon, include `sslmode=require`), a unique `AUTH_JWT_SECRET` of at least 32 bytes, and the exact frontend origin in `AUTH_ALLOWED_ORIGINS`. Generate the JWT secret with `node -e "console.log(require('node:crypto').randomBytes(32).toString('base64url'))"`. Add a Gemini API key to `GEMINI_API_KEY` to enable AI features. Keep database credentials, JWT secrets, and Gemini keys in the backend only; never use `VITE_` for secrets. The LAN development origin `http://192.168.2.2:5173` is also allowed by the backend.
2. Copy `frontend/.env.example` to `frontend/.env`. The Vite proxy defaults to the local backend at `http://localhost:3001`.
3. Start the backend and frontend in separate terminals with `npm run dev` from their respective folders.

To use the three-role demo without a database, explicitly set `EDUFLOW_DEMO_MODE=true` in the backend and `VITE_EDUFLOW_DEMO_MODE=true` in the frontend, then restart both development servers. The role selector is only compiled into Vite development builds. Demo accounts use synthetic identities and cannot access database-backed administration APIs. Demo authentication is rejected when `NODE_ENV=production`; the demo flag must never be enabled on a production backend.

## Database initialization

Run `npm run migrate` from `backend` to apply repository migrations. The runner uses a transaction and advisory lock, requires a Neon TLS connection, and records ordered migration names and checksums. It supports upgrading a schema created by migration 001, takes short-timeout table locks for data preflight and constraint changes, and stops without changing existing rows when the preflight finds conflicts. Migration 003 backfills the new membership role from `users.role`; it does not change membership status or remove rows. Migration 001 remains the bootstrap migration and is not modified by later schema changes.

Migration 025 adds class and semester-scoped timetables with one morning or afternoon session per semester. After applying migrations, the 11A2 semester-1 schedule can be seeded only in a non-production environment by explicitly setting `EDUFLOW_ALLOW_TIMETABLE_SEED=true` and running `npm run seed:timetable:11a2` from `backend`. The seed verifies the target school and class, is transactional and refuses to overwrite a different existing timetable. Semester 2 and period times are not seeded because they were not supplied.

Migration 026 adds teacher-owned weekly schedules with editable lesson topics, make-up lessons, homework/exam slots, and a weekly note. Teachers can save a draft or publish it to their assigned classes; student timetable and planning APIs only expose published items for the authenticated student's active class. For the non-production Đức example schedule, apply migrations, then set `EDUFLOW_ALLOW_TEACHER_TIMETABLE_SEED=true` and run `npm run seed:timetable:teacher-duc`. It verifies Đức's 11A2 homeroom assignment and Hóa học assignments in 11A2, 11A5, and 12A1, aligns the 11A2 periods with the existing class timetable, and creates a clearly marked estimated morning draft for the current week only. The seed refuses to overwrite a teacher-edited schedule. AI planning uses authenticated, class-scoped progress and assignment data; it does not invent lesson topics or deadlines.

Migration 027 adds date-specific class timetable events while retaining the recurring class timetable from migration 025 and the teacher's editable weekly schedule from migration 026. Publishing a teacher week replaces only that teacher's event rows for the corresponding dates; drafts are not visible to students. Events can override a recurring cell, add a make-up lesson, cancel a cell for that week, and record lesson topics, homework deadlines, tests, and test-return times. The student timetable merges the authenticated student's active class skeleton with published events for the requested Monday-to-Sunday date range; historical weeks remain unchanged. The displayed academic week number is derived from the academic year's September 5 rule: if September 5 is Friday through Sunday, week 1 starts the following Monday; otherwise it starts that week's Monday. Apply migrations with `npm run migrate` before deploying this version.

Migration 028 adds database-backed AI chat history, scoped to the authenticated user and role for both students and teachers. Existing student chat history is imported from that browser the first time the student chat opens and is removed from browser storage only after the import succeeds. Apply migrations with `npm run migrate` from `backend` before using AI chat history.

Migration 029 adds optional JPEG, PNG, and WebP image attachments to AI chat messages. Images are stored in PostgreSQL (maximum 5 MB each), are available when reopening the conversation, and are deleted with their conversation. Apply migrations with `npm run migrate` from `backend` before using image attachments.

Migration 030 adds database-backed appeals for published online exam results. Students can submit one appeal per graded exam and follow the teacher's response; only the teacher who owns the exam room can review it. Apply migrations with `npm run migrate` from `backend` before using exam appeals.

Migration 031 allows nonempty appeal reasons from 1 to 2,000 characters, matching the student form and API validation. Apply migrations with `npm run migrate` from `backend` to update existing databases.

Migration 034 adds `users.avatar_url` for account-wide profile avatars. Apply migrations with `npm run migrate` from `backend` before starting the updated backend; authentication reads this column when loading the account.

Migration 033 adds metadata-only `exam_logs` for `tab_hidden`, `face_missing`, `multiple_faces`, and `speech_activity`. Students send events through `POST /api/student/exam-sessions/:sessionId/behavior-logs`; the endpoint validates the active student's session and the room's monitoring settings, and suppresses repeats of the same event type within three seconds. Face and speech detection are optional room settings and run locally in the browser; no image, video, or audio is uploaded or stored. These logs do not change exam status or calculate a trust score. Apply migrations with `npm run migrate` before enabling the new monitoring options.

Teacher progress analysis uses the selected class, subject, and semester gradebook, assignment submission/feedback data, and (for the class's homeroom teacher) cross-subject averages. It compares each student's current TBM with the most recent changed TBM snapshot when available, reports the exact difference, and does not infer a long-term trend from one comparison. Cross-subject averages are current-only. Analysis is generated only when requested; student names and email addresses are omitted from the AI prompt, and the server maps anonymous student keys back for the authorized teacher. AI suggestions are advisory and do not trigger student or classroom actions.

PostgreSQL integration tests use only a separate loopback database whose name is `eduflow_test` or `eduflow_test_<suffix>`. Set `EDUFLOW_TEST_DATABASE_URL` for that test database and run `npm run test:postgres` from `backend`. Each run creates and drops a random isolated schema inside that explicitly named test database. The test command rejects Neon and all non-loopback hosts; it never reads or falls back to `DATABASE_URL`. Without this variable, the PostgreSQL tests are skipped.

After the schema is applied, an operator can bootstrap the first system administrator once by setting `BOOTSTRAP_ADMIN_EMAIL`, `BOOTSTRAP_ADMIN_NAME`, and `BOOTSTRAP_ADMIN_PASSWORD` in the local backend environment and running `npm run bootstrap:admin` from `backend`. The command refuses to run if the users table is non-empty. Remove the bootstrap password from the environment immediately afterward.

System administrators can create schools and generate student/teacher invitation links from the user-management page. Each invitation assigns one role; users cannot select or switch roles at login. Invitees set their own password, then complete their profile before entering the app. Student grade/student number and teacher employee number are optional profile fields. The one-time invitation token is only stored as a hash in PostgreSQL; EduFlow does not send email, so administrators must share the generated link through an approved channel.

Migration 012 adds `teacher_profiles.gender` with the values `female`, `male`, `other`, and `unspecified`. To populate the requested 11A2 subject assignments for a non-production test database, first apply migrations, then explicitly set `EDUFLOW_ALLOW_PLACEHOLDER_TEACHER_SEED=true` and run `npm run seed:class-11a2` from `backend`. The script targets the active Trần Phú / Hoàn Kiếm school and class 11A2 for 2026-2027, verifies the existing homeroom teacher is Đức, and adds subject teachers for Tin học, Sinh học, Lịch sử, Tiếng Anh, Toán học, and Ngữ văn. It only creates disabled accounts using reserved `.invalid` email addresses and random undisclosed password hashes; these placeholders cannot sign in. Replace them through the invitation workflow with real teacher identities before using this data outside a test environment. The seed is transactional and safe to rerun.

Migration 013 adds `teacher_assessments` for database-backed saved exams and assignments, scoped to the owning teacher and school. Apply migrations with `npm run migrate` from `backend` before using the saved-assessment pages. Existing saved exams and assignments in browser storage are uploaded on first load and removed from that browser only after the upload succeeds.

Migration 021 adds a JSONB `sections` column to saved teacher assessments. Each section stores its editable title, instructions, linked question IDs, and embedded question snapshots; the original flat `payload.questions` list remains synchronized for grading and older consumers. Saved exams and assignments use the same section editor, and existing flat assessments are grouped by their populated question types until they are next saved. Run `npm run migrate` from `backend` before deploying this version.

Migration 014 adds database-backed teacher exam-room configurations. Migration 015 adds unique school room codes, student exam sessions, submissions, and security-event logs. Students see only rooms for their active classes; exam answer keys are never sent to the student client. Teachers can review submitted sessions and events in the room monitor. Room scheduling uses one start time and a per-student duration; each student receives that duration from the time they begin, and the teacher controls when the room opens or closes. Webcam/microphone settings only request local device access and preview; the app does not record or upload audio/video. Apply migrations with `npm run migrate` from `backend` before using exam-room setup and student exam rooms.

Expired invitations are retained for history and closed when a replacement invitation is created. Accepting an invitation rechecks that its school is active while holding a transaction lock; suspended schools cannot receive new invitations or accept existing ones.

## Read-only school and class APIs

The backend exposes these authenticated, account-ready endpoints:

- `GET /api/classes` lists active classes visible to the caller. System administrators see active classes across active schools; school administrators are limited to their active school memberships; teachers see classes with an active assignment; students see classes with an active membership. An optional `schoolId` filter cannot expand the caller's scope.
- `GET /api/classes/:classId` returns an active class only when it is within the caller's scope.
- `GET /api/classes/:classId/students` returns active, non-disabled students in a class. Only administrators in scope and assigned teachers can read rosters.

Students and teachers must resolve to exactly one active school for authentication and school/class reads. If they have zero or multiple active schools, auth rejects the scope and class reads return `409 SCHOOL_MEMBERSHIP_INVARIANT_VIOLATION` rather than selecting a school. The versioned schema migration adds a role-aware database uniqueness constraint for active student/lecturer memberships; school administrators may still belong to multiple schools.

These endpoints are read-only. Class creation, membership changes, teacher assignment changes, and frontend integration are not part of this API phase.

## Teacher assignment grading

Run `npm run migrate` to apply migration 008, which adds teacher scores and feedback to submitted class assignments, and migration 017, which stores assignment submission attachments. Assigned teachers can retrieve an assignment's student work with `GET /api/classes/:classId/assignments/:assignmentId/submissions` and save a score from 0 to 10 plus feedback with `PUT /api/classes/:classId/assignments/:assignmentId/submissions/:studentId/grade`. Both routes require an active teacher assignment for the class subject. Students see confirmed scores and feedback from `GET /api/assignments`; resubmitting an answer clears the prior grade so the updated work can be reviewed again.

Teachers can update a class assignment with `PUT /api/classes/:classId/assignments/:assignmentId`, rename active assignment chapter/lesson groups with `PATCH /api/classes/:classId/assignment-chapters/:chapter` and `PATCH /api/classes/:classId/assignment-chapters/:chapter/lessons/:lesson`, or delete an assignment/group using the matching `DELETE` routes. Deleting an assignment also permanently deletes its submissions, grades, feedback, and uploaded files. These write routes enforce the teacher's active subject assignment; the frontend confirms destructive actions before sending them.

Migration 024 adds per-question scores and teacher feedback for assignments. Run `npm run migrate` before deploying this grading version; until it is applied, assignment reads and grading requests that select these fields will fail because the columns do not exist.

Students can attach up to five images or office/PDF files (10 MB each) when submitting or updating an assignment. The existing submission endpoint accepts multipart fields `responseText` and repeated `files`; new attachments are appended on updates. Teachers can fetch each attachment through `GET /api/assignments/:assignmentId/submissions/:studentId/files/:fileId`; students can fetch their own files through `GET /api/assignments/:assignmentId/submission/files/:fileId`. Both routes enforce the active class membership/teacher subject assignment before returning private file bytes.

Students can normalize notation in an answer with `POST /api/ai/format-answer` and `{ "text": "..." }`. The endpoint requires an authenticated student account and limits input to 12,000 characters. It uses `GEMINI_FORMAT_MODEL` when configured, otherwise `gemini-3.5-flash-lite`; other AI features continue to use `GEMINI_MODEL`.

## Teacher online exam grading

Migration 016 adds `teacher_exam_session_grades` to persist per-question scores, total score, teacher feedback, grader, and grading timestamp for submitted online exam sessions. Migration 018 stores student image attachments for essay answers. Teachers can load the roster and submitted answers for their own rooms with `GET /api/teacher/exam-rooms/:roomId/grading` and save or update a grade with `PUT /api/teacher/exam-rooms/:roomId/sessions/:sessionId/grade`. The API validates every question score against the saved exam snapshot and only accepts sessions already submitted by a student.

Migration 019 adds per-essay-question feedback and private teacher evidence images to online exam grades. Teachers can attach up to five JPG, PNG, GIF, or WebP images (10 MB each) while saving a grade; the same grading API returns evidence metadata, and the room teacher can view image bytes from `GET /api/teacher/exam-rooms/:roomId/sessions/:sessionId/grade-files/:fileId`.

Migration 022 adds a per-submission `published_at` timestamp. Saving a grade does not publish it; teachers can publish all currently graded submissions in their room with `POST /api/teacher/exam-rooms/:roomId/publish-grades`. Newly graded submissions stay hidden until published, and students can view only their own published result through `GET /api/student/exam-results`.

Migration 023 stores each student's read state for a published exam grade on the server. `POST /api/student/exam-results/:sessionId/read` marks the currently published grade as read; updating the grade creates a new unread revision. The read state is returned as `grade.isRead` in the student's exam-results response and is shared across the student's devices.

Students may submit up to five JPG, PNG, GIF, or WebP images (10 MB each) with their exam answers using the existing student exam submission endpoint as multipart fields `answers`, repeated `files`, and matching repeated `fileQuestionNumbers`. Images are stored with the submitted session and can be fetched by its room teacher through `GET /api/teacher/exam-rooms/:roomId/sessions/:sessionId/files/:fileId`; the endpoint checks room ownership and only serves submitted work.

Migration 020 adds temporary, expiring phone-upload sessions for essay images. The authenticated student creates a one-question upload session with `POST /api/student/exam-sessions/:sessionId/mobile-upload-sessions`; its random 256-bit capability token is encoded into `/upload-mobile?session=...`. The phone uploads one validated image to `POST /api/upload-temporary`, while the exam computer polls `GET /api/check-session?session=...` and previews the private temporary image. Temporary images are copied into the existing submitted-image table only when the student submits the whole exam; `POST /api/delete-temporary` lets the owning student discard an image first. Expired temporary sessions are removed opportunistically when a new upload session is created and by a 15-minute backend cleanup task.

## Homeroom class overview

Migration 009 adds the class subject catalog and one homeroom teacher/subject assignment per class. Existing active teacher-subject assignments are copied into the class subject catalog; school operators must register additional curriculum subjects and designate the homeroom teacher and subject in `class_subjects` and `class_homeroom_assignments`. Homeroom teachers can read an aggregate class grade summary with `GET /api/classes/:classId/homeroom-gradebook?academicYear=...&semester=...`; access is limited to the designated teacher. Averages use the gradebook weights (regular ×1, midterm ×2, final ×3), and subjects without scores return `null`.

Migration 010 adds `student_term_grades.confirmed_average` for the weighted average calculated and saved with the component scores. Migration 011 adds `previous_confirmed_average`, retaining the TBM from immediately before the most recent save for that student, subject, and term. Migration 032 adds `student_term_grade_history`, seeded with each existing saved average and appended only when a grade update changes the TBM. Re-saving an unchanged average does not create another history row. The gradebook returns this history for the teacher progress chart. Teachers save changed rows together through `PUT /api/classes/:classId/gradebook`; the operation validates the active roster and assigned subject, then persists the submitted rows and history in one transaction.

## Deployment

Set `DATABASE_URL`, `AUTH_JWT_SECRET`, and a comma-separated exact `AUTH_ALLOWED_ORIGINS` list in the backend deployment environment. The production frontend origin `https://edu-flow-dun.vercel.app` is included by default; add any custom frontend domains to `AUTH_ALLOWED_ORIGINS`. Behind a single reverse proxy, set `TRUST_PROXY_HOPS=1` so rate limits use the caller IP. For a frontend and API on separate sites, configure `AUTH_COOKIE_SAME_SITE=none` and `AUTH_COOKIE_SECURE=true`, and retain the Origin check and credentialed CORS allowlist. Do not place database credentials or signing secrets in frontend variables.
